# 2026-10-14 — [#132](https://github.com/kastoestoramadus/hocon-fmt/pull/132) — sbt 2 plugin over the Java API

**Change:** The `sbt-plugin` project cross-builds a flavour for sbt 2 (Scala 3.8.4) beside the sbt 1.x one and publishes it as `sbt-hocon-fmt_sbt2_3`, under the coordinates users already write (`addSbtPlugin("eu.ww86" % "sbt-hocon-fmt" % …)`). The sources stay shared; the task plumbing is per host in `src/main/scala-2.12` and `src/main/scala-3` (`HostSettings`: sbt 1's `retrieve` against sbt 2's `moduleDescriptor`/`update`, and `Def.uncached`, which sbt 2 requires of a task whose result holds a file). The plugin keeps the isolated class loader over the Java API, so sbt 2's Scala 3.8.4 never reads the Scala 3.9 core's TASTy: a 3.8.4 build against `eu.ww86:hocon-fmt-core_3` fails with "Forward incompatible TASTy file has version 28.9 … expected stable TASTy from 28.0 to 28.8", the premise the 2026-10-09 plan no longer had. Five scripted suites in `sbt-hocon-fmt2` mirror the sbt 1.x ones against real sbt 2.0.10 builds (`sbt sbt2PluginTest`), and a CI job runs them.

**Look at again before a release:** The sbt 2 flavour ships an empty javadoc jar (`Compile / doc / sources := Seq.empty`): DottyDoc fails on lmcoursier's dataclass TASTy ("undefined: new dataclass.data … at readTasty"). Re-verify at sbt 2.1 GA, which moves to Scala 3.9 and may then read the core directly — the isolated loader and the runtime java-api resolution could go, as `docs/ideas.md#sbt-2-m` suggests. Update 2026-10-16: that idea was removed from docs/ideas.md (the premise about the Mill plugin was wrong; the sbt 2 flavour has shipped as PR 132). Release wiring for the second flavour is still open (`docs/releasing.md`, `release.yml`, `signedReleaseTasks`).
