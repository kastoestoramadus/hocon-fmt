# 2026-10-09 — #81 — the release ships wave 1 until RELEASE_WAVE=2

**Change:** The first publish is wave 1 only — the sbt-built Central artifacts (libraries, the
JVM cli, the Java API, the sbt plugin). One repository variable, `RELEASE_WAVE`, gates the
workflow: unset or `1` runs the sbt version check, signing and upload; `2` turns the wave-2 jobs
and uploads (native, npm, web, GitHub release, Maven, Mill) back on, in the file, skipped. The
manual dry run still signs with the real key and uploads nothing. The version check follows the
same variable and, in wave 1, demands only `build.sbt` and `java-api/build.gradle.kts`; a
fixture-tree test (`scripts/check-release-version-test.sh`) covers the split. docs/releasing.md
documents the wave and warns that the pre-commit hooks cannot install at a wave-1 tag.

**Look at again before a release:** wave 2 is setting `RELEASE_WAVE=2`, committing all six
version places and re-reading this log; the first wave-2 tag must publish PyPI and npm before it
is announced, or every pre-commit user at that tag fails to install. The sbt plugin resolves the
Java API at run time, not through its POM, so wave 1 must never drop the Java API from the sbt
deployment.
