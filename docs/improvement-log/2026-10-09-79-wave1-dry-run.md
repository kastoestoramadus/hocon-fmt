# 2026-10-09 — [#79](https://github.com/kastoestoramadus/hocon-fmt/pull/79) — Wave 1 tried as a consumer

**Change:** The wave-1 JVM artifacts (core, cats, the CLI, the Java API and the sbt plugin) were
published into a private Maven repository and resolved by three scratch consumer builds — a Scala 3
library, an sbt plugin build that both failed and passed `hoconFormatCheck` around a `hoconFormat`,
and the CLI run from its jar. `hocon-fmt-cli_3`'s POM declares `hocon-fmt-cats_3`, so the release
set gained the adapter, `publishRelease` now names the five wave-1 projects instead of every
platform and the zio adapter, and `sbt test` runs `checkReleaseSet`, which fails while any released
project's dependencies are not released too (red: `catsJVM (needed by cliJVM)`). The user-facing
notes are `docs/plans/release-notes-0.1.0.md`; `docs/plans/wave-1-release-checks.md` records the
improvement-log items wave 1 was checked against and what remains, and `docs/releasing.md` carries
the wave column and the dry run.

**Look at again before a release:** `signRelease` and `sonaUpload` stay unverified without the CI
secrets — `gpg` exits 2 without `PGP_PASSPHRASE` — and the Maven and Mill steps of the release
workflow stage wave-2 deployments that should stay unpublished until wave 2. `sbt test` on the
JVM was green here (core 450, cats 18, cli 64, acceptance 57; `SconfigDefectsSpec` 19 red by
design), but the Scala.js and Native suites were not run in this pass.
